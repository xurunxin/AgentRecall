## What this is

A versioned, offline-first evaluation harness that measures whether the v1.2 lifecycle works end-to-end. The harness wraps the public service APIs (`SessionService`, `DistillationService`, `LoadoutService`, `SkillService`, `BootstrapService`, `ExternalReferenceService`) — never the CLI shims — so a CLI parsing regression cannot mask a real lifecycle regression.

The harness produces **two outputs per run**:
1. `report.json` — the canonical machine-readable artifact CI publishes as a workflow artifact
2. `report.md` — the human-readable summary the release manager reviews before merging

Both reports are versioned via `lifecycle.report.v1`. A v2 can add fields additively without breaking v1 consumers.

## How to run

```bash
pnpm run eval:lifecycle:quick    # walk the corpus, write report.json + report.md
pnpm run eval:lifecycle:full     # same, but --bail on first failure (CI gate)
```

The script exits 0 when every fixture passes; 1 when at least one fails; 2 when a fixture or manifest fails schema validation (a CI / corpus authoring regression).

## Fixture schema (`lifecycle.eval.v1`)

A fixture is one self-contained scenario. It declares:
- `dimension` — which of the 5 evaluation dimensions (#55 `## Evaluation dimensions`) it exercises
- `workstream` — which v1.2 workstream it touches (ingestion / distillation / loadouts / skills / bootstrap)
- `fixture_class` — happy / policy_fail / interrupt_retry
- `determinism` — `deterministic` (byte-identical reruns) or `stochastic` (mean / variance reported)
- `requires_schema_version` — the on-disk `CURRENT_SCHEMA_VERSION` must be at least this
- `seed` — pre-populated data (memories, loadouts, session bundles)
- `operations` — the ordered service-layer calls to execute
- `expected` — what must be true afterwards (job state, candidate count, safety counters, last error code)

### v0.3.1 fixture-by-fixture notes

- `safety_secret_leak_v1` (happy). A `decision_confirmed` event carries a fake `API_KEY=...` matching the v1 `ENV_SECRET` regex. The SessionService.ingest path tags the event with `contains_secret` and still admits it (the v1 surface flags but does not reject). The instrumented `secret_leak_count` records exactly 1 observation; the fixture asserts the observed value is 1. This is a **positive** counter assertion — a passing fixture is the strict inequality `counter > 0`, not `counter = 0` (the latter would prove the counter is not wired).
- `safety_injection_blocked_v1` (happy). A `decision_confirmed` event matches the v1 prompt-injection regex (`ignore all previous instructions`). The instrumented `injection_bypass_count` records exactly 1 observation; every other safety counter is 0.

### Safety counter instrumentation (issue #55b)

The five counters defined by #55 are wired into the v1.2 service layer via dependency injection. A `SafetyCounters` interface (`src/services/safety-counters.ts`) exposes `inc(kind, by?)` + `snapshot()` + `reset()`; the default is `noopSafetyCounters` and the eval harness wires a `CollectingSafetyCounters` per fixture context.

| Counter | Mount point | Rationale |
|---|---|---|
| `secret_leak_count` | `SessionService.ingest` (per event in `persistEvent`) + `DistillationService.runOnBundle` (per candidate body) | Every secret-bearing content the scanner tagged is observed exactly once |
| `injection_bypass_count` | `SessionService.ingest` (per event matching the injection regex) | The v1 scanner flags but does not reject; the counter records the observation |
| `cross_project_leak_count` | `ContextAssembler.assembleBootstrap` (per `MemoryEntry` failing the project-scope guard) | Belt-and-braces check against the `listActiveEntries` filter |
| `sensitivity_leak_count` | `ContextAssembler.assembleBootstrap` (per `MemoryEntry` whose sensitivity exceeds the caller's `max_sensitivity`) | Belt-and-braces check against the visibility filter |
| `unauthorized_trust_escalation_count` | `DistillationService.applyOneAction` (per candidate with `proposed_trust_level = user_confirmed`) | The v1 distillation contract disallows that value, so the counter is permanently 0 today; the hook is the future-proofing surface for a provider-backed extractor |

The runner's `compareOutcomes` step now reads the per-fixture `result.safety_counters` snapshot (taken at `runCorpus` end-of-fixture, not in `runOperation` itself) and matches every field against the fixture's `expected.safety` row. A mismatch is a hard fail.

### Fixture-by-fixture notes

- `session_ingest_secret_redact_v1` (happy, **not** policy_fail). The v1 `SessionService.ingest` path tags a secret-bearing event with `contains_secret` and admits the session; the policy failure (no candidate, no memory entry) is exercised in the distillation fixtures instead. The eval harness does not yet read event-level redaction flags, so the "policy" assertion lives one layer down.
- `distill_no_hallucination_v1` (happy). The deterministic baseline refuses to produce a candidate from a non-`decision_confirmed` event. The fixture asserts `candidate_count = 0`; the runner uses this to argue `distillation_hallucination_rejection_rate = 100%` once the baseline thresholds are formalised.
- `distill_partial_apply_v1` (interrupt_retry). A `distill` step is **not** seeded; the operation calls `apply_candidate` with a sentinel `candidate_id`. The service throws `candidate_not_found` and the active memory store is untouched. The fixture proves the apply path cannot partially commit when the candidate is absent.
- `bootstrap_scan_idempotent_v1` (happy). The runner runs `scan` twice and asserts the idempotence contract: the two `plan_id`s differ (a fresh plan row each time) but `config_digest`, `source_set_digest` and `item_count` are byte-equal. The runner sets `bootstrap_hash` to the literal `"MATCH"` on success; a mismatch becomes `DRIFT:…` in the report.
- `bootstrap_apply_partial_v1` (interrupt_retry). The `dispatch.remember` closure throws on the first call; the service's atomic-batch path rolls the entire transaction back. The runner observes the plan state post-apply and suffixes the error message with `|plan_state=<state>` so a future assertion can read the recovery state directly.

## v0.4.0 / v0.5.0 / v1.0.0 — what comes next

The v0.3.0 corpus satisfies #55 AC for the workstream × class matrix. The remaining EPIC items live in their own sub-issues and are out of scope for v0.3.0:

- **#55b** — `safety counter instrumentation (dimension E)`. The runner currently surfaces the `expected.safety` row but does not yet observe real counters; the instrumentation lands with the dimension-E fixtures. The five counter names (`cross_project_leak_count`, `sensitivity_leak_count`, `secret_leak_count`, `injection_bypass_count`, `unauthorized_trust_escalation_count`) are already part of the v0.2.0 `ExpectedOutcomesSchema`.
- **#55c** — `v0.4.0 quality baselines`. The runner writes the baselines declared in `manifest.json` (currently `distillation_supported_claim_rate = 0.9`, `distillation_hallucination_rejection_rate = 0.95`, `bootstrap_hash_byte_determinism = 1.0`) but does not score them. v0.4.0 closes the loop: the runner measures each baseline, fails the run when a threshold is missed, and records the measured number in `report.json`.
- **#55d** — `v1.0.0 CLI + CI integration`. `agent-recall eval` is a development script today; v1.0.0 promotes it to a user-facing CLI subcommand and adds the CI gate, trend comparison and artifact retention.

## Baseline policy (from #55 `## Baselines and gates`)

Initial baselines are deliberately conservative and will be raised once the corpus + harness have produced enough data to justify a move:

```json
{
  "distillation_supported_claim_rate": 0.9,
  "distillation_hallucination_rejection_rate": 0.95,
  "bootstrap_hash_byte_determinism": 1.0
}
```

The release gate fails when any metric drops below its baseline. Any threshold change is versioned and reviewed.

## Out of scope (deferred)

- Optional model-provider evaluations (`eval:lifecycle:provider`) — separate from the deterministic core gate, runs only when explicit credentials are present (Phase 3 follow-up)
- Network-required fixtures (all v1 fixtures MUST run without a hosted model)
- Trend artifact comparison against the last accepted baseline (CI-side, not harness-side)
- Failure reports usable by Coding Agents without access to hidden CI logs (Phase 3 follow-up)
