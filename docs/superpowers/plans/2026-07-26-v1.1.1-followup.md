# v1.1.1 follow-up: public-path correctness and release readiness

**Tracking issue**: [#18](https://github.com/xurunxin/AgentRecall/issues/18)
**Branch base**: `main` @ `feea9b6` (v1.1.0 release)
**Target release**: `v1.1.1`

## Context

Stage 15 (v1.1.0) shipped 8 PRs (M0 stabilization → M3 intelligence). The v1.1.0 acceptance review
surfaced a recurring pattern: **internal structures and helpers exist, but the real MCP / Service /
SQLite public path is not yet protected by them.** The follow-up work is about wiring the v1.1
primitives into the public boundary, not adding new modules.

8 follow-up issues are tracked under #18, mapped to 4 batches, each batch = 1 PR. Total 4 PRs +
1 release commit, all local until the final push.

## Strategy decisions (locked)

- **PR splitting**: 1 PR per batch (4 PR total), not 1 per issue. Rationale: the issue split
  in the tracker is the **work shape** (which file paths to touch), not the **review shape**;
  one batch = one cohesive behavioral boundary.
- **Remote push**: all 4 PRs + `v1.1.1` tag pushed in one final wave after PR-4 lands and
  passes the full local test suite. Mirrors the v1.1.0 release pattern.
- **Worktree per PR**: each PR lives in its own worktree under `.worktrees/`, branched off
  the previous PR's merge commit.

## Per-PR scope and acceptance

### PR-1 (Batch 1): public-path correctness

Closes #10, #11, #14.

**#10 — Idempotency v2 in every public mutation path**

Replace every production use of `lookupIdempotency` / `recordIdempotency` (in
`src/services/memory-write-service.ts`, `src/services/memory-maintenance-service.ts`,
`src/portability/importer.ts`) with the v2 `reserveIdempotency` / `completeIdempotency`
API. Canonical operation payload must be defined for every mutation:

- `remember` — normalized write body.
- `update_memory` — `{memory_id, patch, expected_revision}`.
- `supersede_memory` — `{old_ids, replacement, reason}`.
- `merge_memories` — `{old_ids, replacement, reason, strategy}`.
- `forget_memory` — `{memory_id, reason, expected_revision}` (must include all three
  in the fingerprint — current implementation fingerprints only the key).

Single transaction flow: `BEGIN IMMEDIATE` → reserve → mutate → write revisions/audit →
persist completed result → commit. No production code may write idempotency state after the
business transaction commits. Legacy `mutation_requests` table can stay behind a
`STABLE_ERROR_CODES` migration adapter for one more cycle, then be removed in the next
schema cleanup.

Crash semantics: a process crash before commit must leave neither the business mutation nor
an orphan reservation. If durable `pending` leases are retained, add `owner` + `expiry` +
takeover + GC; otherwise document that pending rows are GC'd at store open.

Acceptance:
- 8-process concurrent stress test (re-use `feat/m0-pre` template) → exactly 1 committed
  domain mutation per `(actor, tool, key)`.
- Replay returns the original success/failure result without a new revision or audit row.
- Different `tool_name` for same `(actor, key)` does not collide.
- `forget_memory` rejects key reuse with a different `memory_id` / `reason` / `expected_revision`.

**#11 — MCP transport context propagation + trusted tool contracts**

`server.registerTool` callback must forward the SDK `extra` argument. Current state at
`src/tools/register-tools.ts`:

- The wrapper at line 263 calls `run(input, extra, ctx)` correctly inside the
  `envelopeHandler`, but the actual `server.registerTool` call invokes the registered
  callback without `extra` — search `src/tools/register-tools.ts` for the actual
  `server.registerTool(name, config, async (input) => handlers[name](input))` pattern.
- `tool_call_id` is synthesized as `${Date.now()}-${Math.random()...}` (line 253). Replace
  with the real JSON-RPC / SDK request id where available.
- `get_memory` trusts client-supplied `accessed_by`; actor must come from `RequestContext`.
  Either remove `accessed_by` from the contract, or make it a no-op.
- Tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`)
  must be backed by executable behavior tests, not just registration snapshots.
- `plan_maintenance`, `apply_maintenance`, `explain_recall` must receive the real
  per-call context, not process-wide defaults.
- `AbortSignal` and progress notifications must propagate into long-running maintenance,
  import/export, and backup paths.

Acceptance:
- A real stdio MCP client call produces audit metadata with the actual client
  name/version, session id, request id, and tool-call id (where the SDK exposes them).
- Cancelling a long-running tool aborts the work and returns a stable cancellation
  error without a partial mutation.
- Progress notifications are observable from a real MCP client.
- `update_memory` and `forget_memory` preserve CAS / idempotency through the complete
  registered-server path.
- Client input can no longer impersonate another access actor.
- `get_memory` is genuinely read-only (or its access-recording side effect is moved to
  `recall_context` / an explicit usage tool).

**#14 — Project identity resolution wired into all public service paths**

Replace the dual `resolveMemoryScope` / `resolveMemoryScopeWithStore` behavior with a single
injected `ProjectIdentityResolver` consumed by `MemoryReadService`, `MemoryWriteService`,
`MemoryMaintenanceService`, the importer, MCP resources, and CLI commands.

Modes (per call):
- `lookup` — read-only; never creates identity or alias.
- `register` — may create a new identity from a trusted write / setup path.
- `strict_existing` — requires a registered identity; refuses unknown id / path.

Current gaps to fix:
- `src/services/memory-write-service.ts:783` calls `resolveMemoryScope(...)` (store-less).
- `src/services/memory-read-service.ts:278` calls `resolveMemoryScope(...)` (store-less).
- Maintenance and import paths do not consistently enforce the same identity binding.

Creation rule: a new project identity may be created only when the caller supplies a
canonicalizable `project_path` through an authorized setup / write path. `project_id`-only
calls must resolve an existing identity; otherwise `invalid_scope` is surfaced.

Enforce both directions:
- One alias / path cannot belong to two project ids → `project_identity_conflict`.
- One project id keeps one immutable canonical path plus explicit aliases.
- Symlink (`realpathSync.native`), Windows case-folded alias keys, worktree (head commit
  match) handled deterministically.

Acceptance:
- `remember` through a real MCP client rejects a path already bound to another project id.
- `search_memories`, `list_memories`, `recall_context`, maintenance, and import cannot read
  or mutate another project's memories by supplying a stale id / path pair.
- Read-only calls do not create project identities or aliases.
- Authorized registration creates exactly one canonical identity and deterministic aliases.
- Project-id-only calls fail for unknown identities and succeed for registered identities.
- Symlink and worktree paths resolve consistently on Linux, macOS, and Windows.
- No public service path calls the store-less resolver for project scope.

### PR-2 (Batch 2): atomic maintenance apply + strict import

Closes #12, #13.

**#12 — Atomic maintenance apply with correct idempotent replay**

- Persist the canonical apply result for each plan + idempotency key.
- Retry behavior: same `plan_id + idempotency_key + plan_hash` returns the original result
  as a no-op replay; same plan with a different key returns a stable mismatch code; replay
  has no new revision or audit side effect.
- Apply the **whole plan** in one database transaction. Load plan → validate state / expiry
  / hash / scope / every expected revision → reserve idempotency → execute all targeted
  groups → write revisions / audits → mark plan completed and store result → commit.
- Any failure must roll back every mutation performed by the plan.
- Continue to guarantee no memory outside `maintenance_plan_items` can be mutated.
- Use the request actor + request id from `RequestContext` (this is now safe because #11
  has landed in PR-1).
- Document lifecycle states: `pending`, `applying`, `completed`, `rejected`, `expired`.

Acceptance:
- A plan with ≥ 2 duplicate groups either applies all or applies none.
- Injecting a failure in group 2 rolls back group 1.
- Same plan + same key returns the original success result with no new writes.
- Same plan + different key is rejected deterministically.
- Expired / stale / tampered / cross-scope plans mutate nothing.
- Apply never touches an unplanned memory.
- Plan state, revisions, audit, and idempotency result commit atomically.
- Tests cover restart, fault injection, same-key replay, different-key reuse, and
  multi-group rollback through the public service and the MCP stdio path.

**#13 — Strict import bundle validation + recovery history**

- Introduce an explicit import preflight phase: schema + enum, project identity + scope
  binding, secret + unsafe-content policy, sensitivity / export policy, id / revision
  conflict policy, aggregate batch budget impact. All validated before mutation.
- Reuse the live write validators where possible while allowing the importer to preserve
  a source memory id.
- Apply the validated plan in one transaction; write entry changes, revision records,
  audit events, and import provenance / batch metadata.
- Versioned portability contract: snapshot mode preserves current entry fields, writer,
  source revision, trust / sensitivity / tier, and import provenance. Full-history mode
  exports and restores `memory_revisions`, relevant audit events, relations,
  access-independent provenance, and schema / version metadata.
- Mark imported data with `trust_level: imported` unless a stronger trust decision is
  explicitly and safely restored from a signed / trusted bundle.
- Add a stable import batch id and bundle hash to audit / provenance records.
- Keep backward compatibility with v1.0 / v1.1 snapshot bundles through an explicit
  migration adapter.

Acceptance:
- A re-hashed bundle containing a secret is rejected before any row is written.
- A bundle writing a project entry under a conflicting project identity is rejected
  atomically.
- Aggregate batch budget overflow is detected before apply.
- Any validation or CAS failure leaves entries, revisions, audit, relations, and
  provenance unchanged.
- Snapshot round-trip preserves all documented current-entry fields and records import
  provenance.
- Full-history round-trip preserves revision ordering and relevant audit metadata.
- Imported entries cannot silently claim `user_confirmed` trust without a documented
  trusted-bundle mechanism.
- CLI returns non-zero on every rejected or rolled-back import and prints the exact
  failing entry / reason without leaking secrets.
- Tests use malicious bundles, cross-project bundles, secret-containing bundles, budget
  overflow, revision drift, and clean round-trips.

### PR-3 (Batch 3): hybrid retrieval + memory semantics MCP

Closes #15, #17.

**#15 — Real hybrid retrieval on `search_memories` and `recall_context`**

- Introduce a candidate-source abstraction with stable source names and ranks. At least
  two real sources contribute to RRF:
  1. FTS lexical (words, structured identifiers).
  2. FTS trigram / substring (Chinese, compiler error fragments, paths, partial
     identifiers).
- Use real Reciprocal Rank Fusion over multiple ranked lists. The exact value shown in
  `explain_recall` must be the value used by the final score (no more "RRF for
  explanation, lexical for scoring").
- Route both `search_memories` and `recall_context` through the same candidate, fusion,
  policy-rank, and budget-pack pipeline.
- Pass the canonical store signals and current `RequestContext.actor_id` into the actual
  recall ranking (not just the explanation).
- Deterministic scope policy: project exact / fuzzy candidates receive project priority;
  relevant global memories may still compete; unrelated global candidates cannot crowd
  out all project results. **Replace the `[...globalItems, ...projectItems].slice(0, limit)`
  concatenation with real fusion.**
- Wire real feedback / access / trust signals into context selection, not only
  explanation.
- Either implement conflict / unsafe-content penalties from stored relations / risk
  findings, or remove those components from the public explanation.
- Add a versioned ranking explanation: candidate sources, per-source rank, fused score,
  policy signals, penalties, final score.
- Keep local embedding optional behind a provider interface; the deterministic
  lexical + trigram pipeline must work without a model or network.

Acceptance:
- `search_memories` and `recall_context` use one shared ranking pipeline.
- A project query cannot have all project results displaced by global-first concatenation.
- Chinese substring, compiler error fragment, file path, package name, and function
  identifier benchmarks improve over v1.1.
- At least two real candidate lists contribute to RRF.
- The RRF value in explanation is exactly the value used in scoring.
- Access, feedback, and current-actor trust can change actual context selection.
- Placeholder conflict / risk fields are removed or backed by real data.
- Ranking is deterministic for fixed data, query, actor, configuration, and time.
- Regression fixtures cover project / global conflict, Chinese text, code symbols, stale
  memories, unsafe content, and token-budget packing.

**#17 — Memory semantics exposed through MCP**

- Extend `RememberInput`, `UpdateInput`, and MCP schemas with controlled fields:
  `tier`, `pinned`, `valid_from` / `valid_until`, `sensitivity`, and trust transitions
  through explicit policy rather than unrestricted client input.
- Authorization rules:
  - Agents may create `agent_observed` / `inferred` memories.
  - `user_confirmed` requires an explicit trusted user-confirmation path.
  - Restricted memories require an allowed actor / policy context.
- Apply temporal policy before ranking:
  - Future `valid_from` entries are excluded.
  - Expired `valid_until` entries follow one documented rule (exclude / archive / decay);
    explanation states why an entry was excluded or penalized.
- Register trusted MCP operations:
  - `record_memory_feedback`
  - `record_memory_provenance` (and / or automatic-only provenance capture)
  - `explain_memory_provenance`
  - Minimal episode create / close / list if episodes stay in v1.x scope.
- Feedback actor identity must come from `RequestContext`, not arbitrary input actor id.
- Automatically record provenance from available request fields: issue / PR / commit
  source refs, tool call, session, import batch.
- Add memory resources for provenance, hierarchy summary, and temporal state where useful.
- Offer a core / default MCP profile and an extended / maintenance profile so normal
  coding agents are not overloaded with administrative tools.
- Build a reusable benchmark command and fixture set covering fact recall, stale-state
  handling, project isolation, multi-agent trust, Chinese / code retrieval, prompt
  injection resistance, and token-budget efficiency.

Acceptance:
- A real MCP client can create and update working / core / archival memories within policy.
- Unauthorized trust or sensitivity escalation is rejected and audited.
- Future and expired memories follow the documented temporal policy in both
  `search_memories` and `recall_context`.
- Feedback changes actual recall ranking and is attributed to the real request actor.
- Provenance is automatically recorded for normal writes / imports when context is
  available, and can be explained through MCP.
- Tier, trust, sensitivity, validity, and provenance round-trip through the documented
  export / import format.
- Episode functionality is either connected to public behavior with tests, or removed
  from the release contract until implemented.
- Benchmark results are reproducible, versioned, and runnable in CI without a network
  model.
- Public documentation distinguishes implemented behavior from optional future
  intelligence providers.

## Per-PR worktree pattern (preserved from v1.1.0)

- One worktree per PR: `.worktrees/m1-pr{N}`.
- One branch per PR: `feat/m1-pr{N}-<theme>`.
- Commit message lives in `<branch>-COMMITMSG.txt` at worktree root; `git commit -F
  <file>`; `mavis-trash` after.
- Self-verify loop: `npm run typecheck` + `npm test -- --run` + per-PR acceptance list.
- Tag the commit (not the merge), but for v1.1.1 we use a normal merge / fast-forward to
  main and tag the merge commit.
