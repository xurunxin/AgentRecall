# v1.1.1 follow-up: public-path correctness and release readiness

**Tracking issue**: [#18](https://github.com/xurunxin/AgentRecall/issues/18)
**Branch base**: `main` @ `feea9b6` (v1.1.0 release)
**Target release**: `v1.1.1`

## Context

Stage 15 (v1.1.0) shipped 8 PRs (M0 stabilization → M3 intelligence). The v1.1.0 acceptance review
surfaced a recurring pattern: **internal structures and helpers exist, but the real MCP / Service /
SQLite public path is not yet protected by them.** The follow-up work is about wiring the v1.1
primitives into the public boundary, not adding new modules.

8 follow-up issues are tracked under #18, mapped to 4 batches, each batch = 1 PR. Total 4 PRs +
1 release commit, all local until the final push.

## Strategy decisions (locked)

- **PR splitting**: 1 PR per issue (8 PR total), revised after the first read-through
  revealed each follow-up is 300–800 lines of impl + 200–500 lines of tests. The original
  "1 PR per batch" plan would have produced 1000+ line PRs that block review and
  rollback. Each PR closes exactly one issue and ships its own acceptance evidence.
- **Remote push**: all 8 PRs + `v1.1.1` tag pushed in one final wave after PR-8 lands
  and passes the full local test suite. Mirrors the v1.1.0 release pattern.
- **Worktree per PR**: each PR lives in its own worktree under `.worktrees/`, branched
  off the previous PR's merge commit.
- **Naming**: stage 16 uses the `feat/m2-pr{N}-*` prefix (stage 15 used `feat/m1-pr{N}-*`).

### PR-1: MCP trusted context (`#11`)

Closes #11.

**Scope** (single file in `src/tools/`, plus matching test):

1. `src/tools/register-tools.ts`:
   - `server.registerTool(name, config, async (input, extra) => handlers[name](input, extra))` —
     forward the SDK `extra` end-to-end.
   - `buildToolRequestContext` no longer fabricates a `tool_call_id` from `Date.now()` +
     `Math.random()`. Pull the real JSON-RPC / SDK request id from the `extra` envelope
     when available; fall back to the existing `randomUUID()` default in
     `buildRequestContext` only when the SDK exposes none.
   - `get_memory` no longer reads `input.accessed_by`. Access identity must come from
     the `RequestContext` actor (and, per #11, `get_memory` becomes genuinely read-only
     — see below).
2. `src/services/memory-read-service.ts`:
   - `getMemory(id, accessedBy?)` — drop the `accessedBy` parameter; the service no
     longer records access from a read tool.
3. `src/sqlite-store.ts`:
   - Add a new `peekEntry(id)` that returns the entry without side effects; `getEntry`
     either delegates to `peekEntry` + `recordAccess` (when an actor is supplied) or
     becomes pure. The MCP `get_memory` path uses `peekEntry`; the read paths that
     legitimately need to record access (e.g. `recall_context` selecting a memory)
     call the explicit `recordMemoryAccess(memoryId, actorId)` helper instead.
4. `src/tools/schemas.ts`:
   - Remove `accessed_by` from the `get_memory` schema (or keep it as a no-op
     deprecated alias for one release cycle, with a clear warning). Add a
     deprecated alias for the public contract.
5. `src/memory-service.ts`:
   - `getMemory(id)` — drop the second `accessedBy` argument in the public signature.

**Annotation audit (mandatory for `#11` acceptance)**:

- `get_memory` is now `readOnlyHint: true`, `destructiveHint: false`,
  `idempotentHint: true`.
- `remember` / `update_memory` / `supersede_memory` / `merge_memories` /
  `forget_memory` are `idempotentHint: true` only when the call carries an
  `idempotency_key` (PR-3 will gate the actual v2 reservation; PR-1 only fixes the

- `list_memories` / `search_memories` / `explain_recall` / `get_memory_budget` /

The annotation audit ships an executable test in
`test/release-gate/p3-mcp-tool-annotations.test.ts` that walks every tool
registration and verifies the annotation matches the actual behaviour (via
mocked service spies that record side effects per call).

**Acceptance criteria**:

- A real stdio MCP client call (via `StdioClientTransport` against
  `dist/src/index.js`) produces audit metadata containing the actual client
  name / version, session id, request id, and tool-call id (where the SDK
  exposes them).
- Cancelling a long-running tool aborts the work and returns a stable
  cancellation error without a partial mutation. `AbortSignal` is propagated

- Progress notifications are observable from a real MCP client for
  `maintain_memories` / `export_memory_context` / `import_memory_context`.
- `update_memory` and `forget_memory` preserve CAS / idempotency through the

  fix is locked in place).
- Client input can no longer impersonate another access actor: `get_memory`
  does not consult `input.accessed_by`, and `getEntry`'s access-recording

- `get_memory` is genuinely read-only.

### PR-2: Project identity public path (`#14`)

Closes #14.

Depends on PR-1 (`#11`) — the public path now propagates a real
`RequestContext`, so the resolver can use `ctx.actor_id` as the
`recordedBy` source.

**Scope**:

1. `src/scope-resolver.ts`:
   - Introduce `ProjectIdentityResolver` class with three resolution modes:
     - `lookup` — read-only; never creates an identity or alias.
     - `register` — may create a new identity from a trusted write / setup
       path. This is the new default for `remember` from MCP.
     - `strict_existing` — requires a registered identity; refuses unknown
       ids / paths. This is the new default for `search_memories` /
       `list_memories` / `recall_context` / `export_memory_context`.
   - Keep the existing function-style `resolveMemoryScope` /
     `resolveMemoryScopeWithStore` as thin compatibility wrappers; the new
     class is the canonical entry point.
   - Document the creation rule: a new project identity is only created when
     the caller supplies a canonicalizable `project_path`. A `project_id`-
     only call must resolve an existing identity (`strict_existing`) or
     surface `invalid_scope` (no implicit identity creation from an
     arbitrary id).
2. `src/memory-service.ts`:
   - Construct the `ProjectIdentityResolver` once in the service factory.
   - Inject the resolver into `MemoryReadService`, `MemoryWriteService`, and
     `MemoryMaintenanceService` (constructor change, not service call change).
3. `src/services/memory-write-service.ts`:
   - `resolveRememberInput` uses the injected resolver in `register` mode
     (was: store-less `resolveMemoryScope`).
4. `src/services/memory-read-service.ts`:
   - `listMemories` / `searchMemories` / `exportMemoryContext` use the
     injected resolver in `strict_existing` mode (was: store-less
     `resolveMemoryScope`).
   - `getMemoryBudget` likewise.
5. `src/services/memory-maintenance-service.ts`:
   - Plan / apply paths use the injected resolver in `register` mode
     (forward-compatible with PR-5 #12).
6. `src/portability/importer.ts`:
   - Pre-flight uses the injected resolver in `strict_existing` mode
     (forward-compatible with PR-4 #13).
7. `src/cli/commands/*`:
   - Each command that takes `--project-id` / `--project-path` uses the
     injected resolver in `register` (default for `agent` / `doctor`) or
     `strict_existing` (default for read commands).
8. `src/mcp/resources.ts`:
   - Resource handlers (`memory://health`, `memory://budget`, etc.) use the
     injected resolver in `strict_existing` mode.

**Acceptance criteria**:

- `remember` through a real MCP client rejects a path already bound to
  another project id with `project_identity_conflict`.
- `search_memories`, `list_memories`, `recall_context`, maintenance, and
  import cannot read or mutate another project's memories by supplying a
  stale id / path pair.
- Read-only calls (`list_memories`, `search_memories`, `recall_context`,
  `get_memory_budget`) do not create project identities or aliases.
- `register` mode (used by `remember` and `apply_maintenance`) creates
  exactly one canonical identity and deterministic aliases.
- `project_id`-only calls fail for unknown identities (`invalid_scope`) and
  succeed for registered identities.
- Symlink and worktree paths resolve consistently on Linux, macOS, and
  Windows.
- No public service path calls the store-less resolver for project scope.
- The mode is asserted by tests at each public call site
  (`service.listMemories`, `service.remember`, etc.), not only at the
  resolver helper.

**Files likely to change**:

- `src/scope-resolver.ts`
- `src/memory-service.ts`
- `src/services/memory-write-service.ts`
- `src/services/memory-read-service.ts`
- `src/services/memory-maintenance-service.ts`
- `src/portability/importer.ts` (forward-compat)
- `src/mcp/resources.ts`
- `src/cli/commands/*.ts`

### PR-3: Idempotency v2 in every public mutation path (`#10`)

Closes #10.

Depends on PR-1 (`#11`) and PR-2 (`#14`) — every public mutation now sees
a trusted `RequestContext` and a strict project scope, so the idempotency
reservation can use the canonical `ctx.actor_id` and the canonical project
identity.

**Scope**:

1. `src/services/memory-write-service.ts`:
   - Replace every `checkIdempotency` / `recordIdempotencyIfSet` pair with a
     `runWithIdempotentMutation` helper that wraps the entire mutation in
     `store.transaction(...)`:
       - `reserveIdempotency(store, {actor, tool, key, requestHash, requestId})`
       - run the mutation (write entry, write revision, write audit)
       - `completeIdempotency(store, {actor, tool, key, result})`
       - `COMMIT`
   - Define a canonical operation payload for every public mutation:
     - `remember` — normalized write body (no `idempotency_key` in the hash).
     - `update_memory` — `{memory_id, patch, expected_revision}`.
     - `supersede_memory` — `{old_ids, replacement, reason}`.
     - `merge_memories` — `{old_ids, replacement, reason, strategy}`.
     - `forget_memory` — `{memory_id, reason, expected_revision}` (all
       three in the fingerprint; the v1.1.0 fix only fingerprinted the
       key, which is the bug #10 highlights).
   - The `idempotency_key` itself is excluded from the request hash
     (already true in `checkIdempotency`).
   - The hash input is the canonical JSON of the operation payload, not
     the full input. This means `forget_memory` with a different
     `memory_id` / `reason` / `expected_revision` reuses the same key but
     gets `idempotency_key_reuse`.
2. `src/services/memory-maintenance-service.ts`:
   - The `apply_maintenance` and `plan_maintenance` paths already use
     `checkIdempotency` (via the same `recordIdempotencyIfSet` pattern).
     Apply the same `runWithIdempotentMutation` wrap. The full atomic
     maintenance apply (one transaction for the whole plan) is **PR-5
     (#12)**; PR-3 only fixes the idempotency reservation for the per-step
     write paths.
3. `src/portability/importer.ts`:
   - The importer already runs in a single transaction (PR-M0-3). Switch
     its idempotency reservation to v2 so the per-batch key is in the v2
     namespace. Per-entry idempotency keys are not in scope (the
     non-goals of #10 explicitly say "Import batches may continue using
     their own batch transaction rather than per-entry idempotency
     keys.").
4. `src/services/idempotency.ts`:
   - The deprecated `lookupIdempotency` / `recordIdempotency` wrappers
     are kept for one more release cycle, but every production path now
     uses `reserveIdempotency` / `completeIdempotency`. Add a
     `runWithIdempotentMutation(store, args, work)` helper that combines
     the reservation, the work, and the completion in one transaction
     boundary. The `work` callback receives the reserve result so it can
     short-circuit on `replay` or `rejected`.
5. Crash semantics:
   - A process crash before `COMMIT` rolls back the business mutation
     AND the reservation. The next retry sees `fresh` (the v2 row never
     landed). If a `pending` row does survive (extremely rare — e.g.
     a `node` SIGKILL between `reserveIdempotency` and the work
     callback), the next retry sees `in_flight` and surfaces
     `idempotency_in_flight` so the caller can back off and retry.
   - Document the GC story: at store open, the `pending` rows whose
     `request_id` is older than the takeover window are deleted. The
     takeover window defaults to 60s and is configurable via
     `AGENT_RECALL_IDEMPOTENCY_TAKEOVER_MS`.

**Acceptance criteria**:

- Every public mutation uses `mutation_requests_v2`. The legacy
  `mutation_requests` table has zero production writes (still readable
  through the compatibility wrapper, but no longer written).
- No production path writes idempotency state after the business
  transaction commits.
- Reusing one key across different tools does not collide
  (PR-M0-1 already locked this in via the schema; PR-3 verifies the
  production path honours it).
- Reusing a `forget_memory` key for a different `memory_id`, `reason`,
  or `expected_revision` is rejected with `idempotency_key_reuse`.
- 8-process concurrent stress test (re-use `feat/m0-pre` template):
  exactly 1 committed domain mutation per `(actor, tool, key)`.
- A crash / fault injected before completion leaves the database in a
  retryable and internally consistent state.
- Replayed calls return the exact original result and do not append
  another revision or audit event.
- Tests exercise `MemoryService` and the real MCP stdio path, not only
  `SQLiteMemoryStore` helpers.

**Files likely to change**:

- `src/services/idempotency.ts` (add `runWithIdempotentMutation`)
- `src/services/memory-write-service.ts` (5 mutation methods rewritten)
- `src/services/memory-maintenance-service.ts` (per-step path)
- `src/portability/importer.ts` (batch-level)
- `src/sqlite-store.ts` (optionally add `expirePendingIdempotency()`;
  see "Crash semantics" above)
- New test: `test/release-gate/p3-idempotency-public-path.test.ts`
- New test: `test/release-gate/p3-idempotency-crash-recovery.test.ts`
- New test: `test/release-gate/p3-idempotency-mcp-stdio.test.ts`
- (Re-use `feat/m0-pre` stress fixture for the 8-process test)

     access-independent provenance.
3. `src/portability/manifest.ts`:

### PR-5: atomic maintenance apply (`#12`)

Closes #12.

Depends on PR-1 (`#11`) and PR-3 (`#10`). PR-3 provides the v2
`runWithIdempotentMutation` helper; PR-5 uses it for the whole-plan
apply.

**Scope**:

1. `src/services/memory-maintenance-service.ts`:
   - Persist the canonical apply result for each plan + idempotency key
     (add `completed_at` + `applied_result_json` columns to
     `maintenance_plans`).
   - Rewrite `applyMaintenance` as a single transaction: load plan →
     validate state / expiry / hash / scope / every expected revision →
     reserve idempotency → execute all targeted groups → write revisions
     / audits → mark plan completed and store result → commit. Any
     failure rolls back every mutation in the plan.
   - Retry behavior: same `plan_id + idempotency_key + plan_hash` returns
     the original result as a no-op replay; same plan with a different
     key returns a stable mismatch code (`idempotency_key_reuse`).
     Replay never adds a revision or audit row.
   - Lifecycle: `pending` → `applying` → `completed` / `rejected` /
     `expired`. Document the recovery rules for an interrupted apply
     (a `node` SIGKILL between `applying` and `completed`).
2. `src/maintenance-plan-store.ts`:
   - Add `completed_at` + `applied_result_json` columns (non-destructive
     `ALTER TABLE ... ADD COLUMN` with `NULL` defaults).
   - Add `setMaintenancePlanState(plan_id, state, completed_at?,
     applied_result_json?)` and `expireOldMaintenancePlans(now)`.
3. `src/services/idempotency.ts`:
   - Reuse the `runWithIdempotentMutation` helper from PR-3 for the plan
     reservation.

**Acceptance criteria**:

- A plan with >= 2 duplicate groups either applies all or applies none.
- Injecting a failure in group 2 rolls back group 1.
- Same plan + same key returns the original success result with no new
  writes.
- Same plan + different key is rejected deterministically.
- Expired / stale / tampered / cross-scope plans mutate nothing.
- Apply never touches an unplanned memory.
- Plan state, revisions, audit, and idempotency result commit
  atomically.
- Tests cover restart, fault injection, same-key replay, different-key
  reuse, and multi-group rollback through the public service and the MCP
  stdio path.

### PR-6: real hybrid retrieval (`#15`)

Closes #15.

Depends on PR-1 (`#11`), PR-2 (`#14`), and PR-3 (`#10`).

**Scope**:

1. `src/services/recall-ranker.ts`:
   - Introduce a candidate-source abstraction with stable source names
     and ranks. At least two real sources contribute to RRF:
     - `fts_lexical` — words, structured identifiers.
     - `fts_trigram` — Chinese, compiler error fragments, paths,
       partial identifiers (new FTS5 virtual table with
       `tokenize='trigram'`, or a parallel `trigram` table).
   - Use real Reciprocal Rank Fusion over multiple ranked lists. The
     exact value shown in `explain_recall` is the value used by the
     final score (no more "RRF for explanation, lexical for scoring").
   - Replace the `[...globalItems, ...projectItems].slice(0, limit)`
     concatenation in `searchMemories` with the real fusion output.
   - Pass the canonical store signals (access, feedback, trust) and the
     current `RequestContext.actor_id` into the final score, not only
     the explanation.
   - Either implement conflict / unsafe-content penalties from stored
     relations / risk findings, or remove those components from the
     public explanation.
2. `src/services/memory-read-service.ts`:
   - `searchMemories` and `recallContext` go through the same
     candidate → fusion → policy-rank → budget-pack pipeline. The
     shared pipeline is the only path that calls the ranker.
3. `src/sqlite-store.ts`:
   - Add the FTS5 trigram source. Non-destructive migration (new
     virtual table, backfilled from `memory_entries`).
4. `src/services/candidate-sources/` (new, optional):
   - Split the candidate-source registry into a dedicated module if
     `recall-ranker.ts` grows beyond ~400 lines.

**Acceptance criteria**:

- `search_memories` and `recall_context` use one shared ranking
  pipeline.
- A project query cannot have all project results displaced by
  global-first concatenation.
- Chinese substring, compiler error fragment, file path, package name,
  and function identifier benchmarks improve over v1.1.
- At least two real candidate lists contribute to RRF.
- The RRF value in explanation is exactly the value used in scoring.
- Access, feedback, and current-actor trust can change actual context
  selection.
- Placeholder conflict / risk fields are removed or backed by real
  data.
- Ranking is deterministic for fixed data, query, actor, configuration,
  and time.
- Regression fixtures cover project / global conflict, Chinese text,
  code symbols, stale memories, unsafe content, and token-budget
  packing.

**Files likely to change**:

- `src/services/recall-ranker.ts` (real RRF, candidate sources)
- `src/services/memory-read-service.ts` (shared pipeline)
- `src/sqlite-store.ts` (FTS5 trigram table)
