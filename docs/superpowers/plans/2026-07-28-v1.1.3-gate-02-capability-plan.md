  lines of tests across one new test file + three extended suites.
- **TDD ordering**: RED → GREEN → REFACTOR for the permission
  validation; RED → GREEN for the profile-scoped visibility; RED
  → GREEN for the per-request authorization. Each commit ends

  `main` at `531ce99`. Mirrors the v1.1.1 / v1.1.3 GATE-01 PR
  pattern.
- **No new dependencies**. POSIX `node:fs.lstat` / `node:fs.stat` +
  Windows ACL probe via stdlib + documented CI step. Node 24 has

  `node:fs`; we use the documented wrapper.

  JSON-of-`{token, created_at, label?}`. The new permission
  validation runs at load time, not at write time.
- **Branch protection**. Independent of #31. Each lane produces its
  own PR; the gate plan's `parent:#30` label check is a soft gate
  until #37 finalizes the branch-protection contract.

### Commit 1 — RED scaffold

The file ships **all tests in failing state** so the implementation
can be authored against a stable target. Test layout:

- `describe('CapabilityStore permission boundary')` — 3 POSIX tests
  (0600 accepted, 0644 rejected, symlink rejected) + 2 Windows ACL
  drift tests (gated on `process.platform === "win32"`)
- `describe('activeProfile-scoped visibility')` — 4 tests
  (Core + admin.cap present → normal; Extended + admin.cap present

  restricted; Admin + admin.cap absent → start refuses)
- `describe('per-request authorization')` — 3 tests (per-request
  token on Core works for trust_promotion; per-request token on
  Core rejected when capability type has `profile_required: "admin"`;
  per-request token mismatch audited with stable code)
- `describe('CapabilityStatus drift surface')` — 1 test
  (load-time drift surfaces `kind:"drift"` + `drift_reason` without
  token bytes; `memory://health` reflects drift for operator)
- `describe('constant-time token comparison')` — 1 test
  (authenticate with mismatched token length returns `token_mismatch`
  with constant-time semantics — measure via timing, not strict
  bounds; the test asserts the implementation uses
  `constantTimeEqual` rather than `===`).
- `describe('revoke + restart semantics')` — 2 tests
  (revoke on disk does not affect the running process; restart picks
  up the new state)

To create POSIX file fixtures with specific modes, use
`fs.writeFileSync(path, body, { mode: 0o644 })`. To create symlinks,
use `fs.symlinkSync(target, path)`. To run only the POSIX tests on
Windows (skip the Windows-specific ones), gate them on
`process.platform`.

Verification: `npx vitest run test/release-gate/v113-capability-profile.test.ts`
must report ≥ 10 of the 16 tests failing against the current
implementation. The Windows-gated tests will report as "skipped" on
POSIX; the timing test may pass on current code (skip its assertion

### Commit 2 — GREEN permission validation

```text
src/admin/capability.ts (MODIFIED)
```

Concrete edits:

- Add `validatePermissionBoundary(path: string): { ok: true } |
  { ok: false, reason: "permission_drift" | "acl_drift" | "symlink"
  | "unsupported_owner" }` (exported helper).
- The implementation:
  - `fs.lstat(path)` first. If `lstat` reports `isSymbolicLink()`,
    return `{ok: false, reason: "symlink"}`.
  - `fs.stat(path)` next. On POSIX: check `mode & 0o077 === 0`. On
    Windows: invoke the ACL probe (`getSecurityDescriptor` via the
    documented wrapper, or the established project helper if
    present). Owner check: `process.getuid() !== undefined &&
    stat.uid !== process.getuid()` returns `unsupported_owner`.
  - Returns `{ok: true}` on success.
- `CapabilityStore.load()` calls `validatePermissionBoundary` BEFORE
  parsing the JSON. A failed validation sets
  `{kind: "drift", drift_reason, path}` instead of `{kind:"missing"}`.
- `CapabilityStatus` type union gains `{kind: "drift", drift_reason,
  path}`. The drift reason is the stable code, not the underlying
  `fs` error.

Verification: POSIX tests in `v113-capability-profile.test.ts` pass
on POSIX; Windows tests are still gated on `process.platform ===
"win32"`. `npm test` for the existing `capability.test.ts` +
`mcp-v2-contract.test.ts` stays green (these tests use
`InMemoryCapabilityStore` and don't touch file permissions).

### Commit 4 — GREEN per-request authorization

```text
src/admin/capability.ts (MODIFIED)
src/services/memory-write-service.ts (MODIFIED)
```

Concrete edits:

- `CAPABILITY_TYPES` map gains an optional `profile_required?: "admin"`
  per type. The v1.1.3 contract:
  - `trust_promotion` → `profile_required: "admin"` (only the
    Admin-profile process can authorize a trust tier promotion)
  - `sensitivity_restricted` → `profile_required: "admin"`
  - `import_trust_restore` → no `profile_required` (per-request
    works on any profile)
  - `import_restricted` → no `profile_required`
  - `sensitivity_visibility` → `profile_required: "admin"`
- `CapabilityStore.authorize(input, profile?)` accepts an optional
  `profile` parameter. If the capability type has
  `profile_required: "admin"` and `profile !== "admin"`, returns
  `{ok: false, reason: "profile_mismatch"}`.
- `src/services/memory-write-service.ts`: every privileged-write
  `authorize(...)` call passes `profile: ctx.activeProfile`. The
  envelope rejection surfaces as `profile_mismatch` to the caller.
- The `AuthorizationRequest` type gains an optional `profile?` field
  (or the `authorize` signature takes it as a separate arg).

Verification: per-request authorization tests pass; existing
`p3-strict-import.test.ts` (capability tests) still pass.
