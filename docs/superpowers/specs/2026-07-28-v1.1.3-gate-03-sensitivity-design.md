## Why

The pre-v1.1.3 sensitivity filter existed in scattered places.
v1.1.2 (issue #23 + review by `ora-8`) added a SQL-boundary filter to
the read surface via `actorMaxSensitivity` threaded into
`peekEntry` / `listEntries` / `searchEntries`. v1.1.3 GATE-02 made
the active profile an explicit input (`activeProfile`), so
`MemoryService` now derives `actorMaxSensitivity` from
`(activeProfile === "admin" && hasCapability()) ? "restricted" : "normal"`.

That gave us a single input (`activeProfile`) and a single derived
visibility ceiling (`actorMaxSensitivity`). The pre-#33 contract
was: filter at SQL boundary for the three core read paths, plus
per-request capability overrides where the request supplied a
token.

What #33 closes: **the same visibility ceiling is NOT yet
threaded through every content-bearing path.** Maintenance
helpers (`find_duplicates`, plan/apply diagnostics, the budget
cleanup candidates), MCP templated resources, the Markdown
index/context export, CLI show/list/search/export/diagnostics,
the `explainProvenance` surface, the backup inspection surface, and
several `peekEntry` overloads within write + maintenance paths can
still leak hidden rows or restricted titles / ids / counts.

#33 makes the authorization decision ONE canonical, typed result
that every content-bearing path consults, with the SQL-boundary
filter as the ONLY place sensitivity is decided.

## Out of scope

- New schema. The existing `sensitivity` column on `memory_entries`
  is sufficient. The visibility decision is runtime-only.
- Identity (#31) and capability (#32) layers — already on `main`.
  This lane consumes them.
- New dependencies.
- Bypassing the existing per-request capability token escape hatch.
  A per-request capability still authorizes the operation; #33
  makes the boundary ordering consistent, not new-authoritative.

### Behavioural contract

**Canonical authorization decision** (every content-bearing path):

```ts
type AuthorizationDecision = {
  // The maximum sensitivity class the caller may read or write.
  max_sensitivity: "normal" | "private" | "restricted";
  // Whether a per-request capability token was supplied.
  capability_token_present: boolean;
  // Stable, loggable reasoning for the operator / forensic.
  // NEVER includes the token itself.
  reasoning: string;
};
```

**Maintenance classification** (the 12 actions):

| Action | Safe in Extended | Restricted to Admin | Capability-required |
|--------|------------------|----------------------|---------------------|
| `view_cleanup_candidates` | yes (normal-only listing) | — | — |
| `plan_archive_low_value` | yes (dry-run) | — | — |
| `plan_merge_duplicates` | yes (dry-run) | — | — |
| `plan_apply_maintenance` | yes (dry-run, normal-only) | — | — |
| `apply_archive_low_value` | yes (normal-only) | — | — |
| `apply_merge_duplicates` | — | yes (Admin profile, normal + private only) | per-request capability token for restricted merges |
| `apply_supersede` | — | yes (Admin profile) | — |
| `apply_forget` | — | yes (Admin profile) | per-request capability token for `sensitivity_restricted` forgets |
| `apply_maintenance` | — | yes | — |
| `preview_budget_bypass` | — | — | yes (`trust_promotion`) |
| `apply_force_forget` | — | — | yes (`sensitivity_restricted`) |
| `rebuild_markdown_index` | yes (limited to visible scope) | — | — |

**Visibility matrix** (Core / Extended / Admin × normal / private / restricted):

| Profile × Sensitivity | Read | Search / List / Recall | Export | Maintenance apply | Import restricted bundle | Admin capability |
|-----------------------|------|------------------------|--------|-------------------|---------------------------|------------------|
| Core × normal         | yes  | yes                    | yes    | yes (apply_archive / apply_merge on normal-only) | n/a (must opt in via `allow_restricted: true` + capability token) | denied |
| Core × private        | denied | denied                | denied | denied          | denied                   | denied |
| Core × restricted     | denied | denied                | denied | denied          | denied                   | denied |
| Extended × normal     | yes  | yes                    | yes    | yes             | n/a                       | denied |
| Extended × private    | denied | denied                | denied | denied          | denied                   | denied |
| Extended × restricted | denied | denied                | denied | denied          | denied                   | denied |
| Admin × normal        | yes  | yes                    | yes    | yes             | yes (with capability)     | yes (per-request) |
| Admin × private       | yes  | yes                    | yes    | yes (with capability) | yes (with capability) | yes (per-request) |
| Admin × restricted    | yes  | yes                    | yes    | yes (with capability) | yes (with capability) | yes (per-request) |

The per-row vs per-bundle distinction: `allow_restricted: true` is
now redundant. The capability token (when supplied per-request)
authorizes restricted rows individually; the bundle-level flag is
deprecated.

### Regression risk

The 18 callers of `MemoryReadService`, the 7 callers of
`MemoryMaintenanceService`, the MCP resource layer, the importer /
exporter, the backup inspector, the CLI commands. Tests most at
risk:

- `p3-sql-boundary-sensitivity.test.ts` (18 tests, v1.1.2 baseline)
  — the SQL-boundary filter surface. The new auth-context must
  preserve the existing predicate behaviour.
- `mcp-all-tools-e2e-core.test.ts` (24 tests after #32) + the
  extended counterpart (33 tests after #32) + `mcp-admin-default`
  (8 tests after #32). The matrix tests extend each to cover
  every visible profile × sensitivity combination.
- `multi-process-stress.test.ts` — pre-existing flaky; do not
  touch.
- `p3-import-batch-lineage.test.ts` (16 tests after #31) +
  `p3-import-preflight-budget.test.ts` (13 tests after #31) +
  `portability-import.test.ts` (8 tests after #31) — the import
  surface. The per-row vs per-bundle change does NOT weaken the
  existing assertions.
- The maintenance service (`p3-atomic-maintenance-apply.test.ts`,
  `p1-maintenance-plan-v2.test.ts`) — every action must round-trip
  through the new `MaintenanceActionPolicy` table.
- The CLI tests (`cli/export.test.ts`, `cli/migrate.test.ts`,
  `cli/import-preflight.test.ts`) — the CLI surface picks up
  the new decision.
