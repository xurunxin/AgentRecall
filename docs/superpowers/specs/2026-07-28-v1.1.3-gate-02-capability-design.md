## Why

`CapabilityStore.hasCapability()` (src/admin/capability.ts:265) returns
true whenever the on-disk `admin.cap` was successfully loaded — even
when the process is running the Core or Extended profile. Two
consequences flow from this:

1. **Visibility leak.** `src/index.ts:147` derives
   `actorMaxSensitivity` from `capabilityStore.hasCapability()`. A
   Core process with a valid `admin.cap` in its data home gains
   `"restricted"` visibility from a path-side constructor decision —
   not from the active profile. The current code conflates "is there
   a file on disk" with "is the active profile Admin". The v1.1.2
   `admin-profile` startup gate (issue #22 + #23) closes the
   Admin-refuses-to-start case but does NOT close the
   Core-with-admin-cap-on-disk case.

2. **Permission validation is JSON-only.** `CapabilityStore` parses
   the file content and decodes the token, but does NOT validate the
   filesystem permission boundary at load time. A `0644` /
   group-readable `admin.cap` is loaded as if it were `0600`. On
   Windows, no ACL check runs at all. Symlinks and reparse points
   are not refused.

This lane closes both gaps and pins the contract for every privileged
write + every privileged read.

## Out of scope

- Detail design for #33 (sensitivity policy across paths). The
  authorization decision in #32 is the source of truth for #33; #33
  will thread it through every content-bearing path.
- New dependencies. POSIX `fs.stat` / `fs.lstat` / Windows ACL probe
  via stdlib only (`node:fs` + `node:os`).
- Local operator multi-user security. README + ADR state this is
  filesystem-bound separation; not cryptographic.

### Behavioural contract (per profile)

| Profile | Valid `admin.cap` present | `admin.cap` missing | `admin.cap` permission-drifted | `admin.cap` malformed |
|---------|------------------------------|--------------------|--------------------------------|----------------------|
| `core` | normal visibility (Core process must NEVER inherit Admin visibility) | normal visibility | normal visibility; the load-time drift is surfaced on `memory://health` for the operator | normal visibility |
| `extended` | normal visibility (Extended gains tools, not visibility) | normal visibility | normal visibility; drift surfaced | normal visibility |
| `admin` | restricted visibility (per-request or Admin-profile authorization) | Admin refuses to start (`process.exitCode = 1`) | Admin refuses to start with `permission_drift` reason | Admin refuses to start with `malformed` reason |

The single explicit authorization decision is the new
`authorizeWithPolicy(input, profile)` method. Every privileged write +
every restricted visibility read MUST go through this call. The
failure envelope is `{ok: false, reason}` where `reason` is one of
the stable codes above.

### Permission validation rules (POSIX)

`validatePermissionBoundary(path)` on POSIX:

- `fs.lstat(path)` is checked first — if the entry is a symlink, the
  load fails with `symlink` (the file's owner could change behind
  the loader's back). A reparse-point on Windows is the same rule.
- `fs.stat(path).mode & 0o077 === 0` is required. `0o644`,
  `0o664`, `0o666` all fail with `permission_drift`.
- The owner must equal the current `process.getuid()`. Mismatched
  ownership fails with `unsupported_owner`.

### Permission validation rules (Windows)

- `fs.lstat(path)` — symlink / reparse-point fails with `symlink`.
- `fs.stat(path)` — `isFile()` must be true (no directories, no
  devices).
- The Windows ACL probe uses `getSecurityDescriptor` via
  `node:fs.promises` in Node 24 (or the documented alternative). A
  non-owner / group-readable / world-readable ACL fails with
  `acl_drift`. The probe runs inside a Windows CI step on the gate
  matrix; on POSIX the ACL probe is a no-op.

### Per-request authorization

A privileged request can be authorized two ways:

1. **Admin-profile authorization** (set at startup): the loaded
   capability grants Admin-bound operations for the lifetime of the
   process. Active profile must be `admin`.
2. **Per-request capability**: the request supplies a capability
   token (the MCP tool's `capability` field); `authorize(...)`
   validates against the loaded `CapabilityStore`. Active profile
   can be `core` / `extended` / `admin` — the per-request path
   doesn't depend on the profile.

The per-request path is the explicit choice for agentic flows that
must work in Core / Extended without sacrificing security. The
Admin-profile path is the operator's convenience.

### Canonical registration / lifecycle

- The single canonical grant path is `agent-recall admin grant`
  (CLI) which writes `admin.cap` with mode `0o600` (POSIX) or
  owner-only ACL (Windows).
- The CLI's `status` command is the single read path for operators.
- The CLI's `revoke` command removes the file; subsequent
  operations see `{kind: "missing"}` until `grant` is re-invoked.
- Restart is required for any change to take effect on a running
  process (the in-memory token is set at startup; revoke only
  removes the file). The doc-comment on `revoke()` is updated to
  spell this out.

### Regression risk

The 18 callers of `CapabilityStore` and the 7 callers of
`InMemoryCapabilityStore` form the blast radius. Tests most at risk:

- `test/admin/capability.test.ts` — the existing capability surface.
  The permission validation is additive; existing tests stay green
  if the file mode is set correctly in each test fixture.
- `test/release-gate/p3-memory-semantics-mcp.test.ts` — uses
  `InMemoryCapabilityStore` for testability; the per-request path
  stays unchanged. The Admin-profile path must NOT silently degrade
  to Core visibility.
- `test/release-gate/admin-default/mcp-admin-default.test.ts` —
  the Admin-profile packaged black-box. The startup gate stays;
  `actorMaxSensitivity === "restricted"` only when
  `hasCapability()` AND `activeProfile === "admin"`.
- `test/blackbox/mcp-all-tools-e2e-extended.test.ts` —
  Extended-profile packaged black-box. Extended gains tools, NOT
  visibility.
- `test/release-gate/p3-sql-boundary-sensitivity.test.ts` — the
  SQL-boundary sensitivity filter. The contract pins hidden rows
  absent at the SQL layer regardless of profile.
- `test/release-gate/p3-import-batch-lineage.test.ts` (15+1 tests
  from #31) — the lineage surface. The new permission validation
  does NOT change import-batches shape; the audit-metadata entry
  from #31 stays unchanged.

## [1.1.3] — v1.1.3 GATE-02: profile-scoped admin capability +

### Changed

- `MemoryService` constructor takes an explicit `activeProfile`
  parameter; the service threads it into every sub-service. A Core

  merely because `admin.cap` exists in its data home.

  "normal"`.
