## Why

`ProjectIdentityResolver.resolve()` accepts a `mode` argument
(`"lookup" | "register" | "strict_existing"`) but the helper it routes
to, `resolveMemoryScopeWithStore` (src/scope-resolver.ts:343–451), does
**not** consult that mode. Every path-supplied call funnels through the
same code that calls `upsertProjectIdentity(...)` and
`registerAlias(...)`. The concrete consequences:

1. A `lookup` call (a read-only operation) can leave a fresh row in
   `project_identities` and `project_aliases_new` if the caller supplied
   a path that hadn't been registered before. Reads mutate state.
2. `strict_existing` has the same behaviour: a strict-mode read of a
   new path silently creates an identity and an alias, then returns
   `ok`. The whole point of `strict_existing` is to *refuse* unknown
   bindings; the current implementation cannot enforce that.
3. Import preflight inherits this — it calls `resolve(...,
   "strict_existing")` and gets an implicit identity registration as a
   side effect. The `ProjectIdentityResolver` doc-comment at
   src/scope-resolver.ts:282–340 already says "lookup and strict_existing
   never create one"; the implementation disagrees.
4. Import apply revalidates revisions and aggregate budget inside the
   apply transaction but **does not** revalidate the identity binding.
   A preflight / apply race that registers a *new* identity (because of
   the bug above) then bumps a different `canonical_path` between
   preflight and apply would silently mutate the identity row under
   the apply transaction.

`#21` (v1.1.2) closed the default-unbound `project_id` fallback but
explicitly carved out apply-time identity revalidation because the
side-effect-on-strict path wasn't a regression for the cases #21
covered. `#31` closes that carve-out.

### Public surface delta

| Surface | Before (v1.1.2) | After (#31) |
|---------|------------------|-------------|
| `ProjectIdentityResolver.resolve(input, mode)` | mode is passed through but ignored by `resolveMemoryScopeWithStore` | mode is consulted; `lookup` / `strict_existing` never reach `upsertProjectIdentity` or `registerAlias` |

| Env var `AGENT_RECALL_ALLOW_UNBOUND_PROJECT_ID` | unchanged | unchanged (the legacy escape hatch is preserved) |

### Behavioural contract

The three modes are now genuinely distinct. The contract is pinned by
`test/release-gate/v113-identity-side-effect-free.test.ts`:

| Mode | Path-supplied unknown | Path-supplied known, id mismatch | Path-supplied known, id matches | project_id-only unknown | project_id-only known |
|------|-----------------------|---------------------------------|--------------------------------|------------------------|----------------------|
| `lookup` | returns `ok` with `identity_status: "absent"` (or similar marker); **0 writes** | returns `project_identity_conflict`; **0 writes** | returns `ok` with `identity_status: "bound"`; **0 writes** | returns `ok` with `identity_status: "absent"`; **0 writes** | returns `ok` with `identity_status: "bound"`; **0 writes** |
| `strict_existing` | returns `project_identity_conflict`; **0 writes** | returns `project_identity_conflict`; **0 writes** | returns `ok` with `identity_status: "bound"`; **0 writes** | returns `invalid_scope` (unless escape hatch) | returns `ok` with `identity_status: "bound"`; **0 writes** |
| `register` | inserts `project_identities` + `project_aliases_new`; returns `ok` with `identity_status: "bound"` | returns `project_identity_conflict`; **0 writes** | inserts only if missing (alias row idempotent); returns `ok` | inserts `project_identities` (with derived id); returns `ok` | inserts alias if missing; returns `ok` |

The apply transaction **never** calls `register`. The apply
transaction only calls `strict_existing` against the resolved scope to
re-validate the binding captured at preflight time.

### Canonical registration path

Documented in `docs/adr/0004-identity-resolution-modes.md` and called
out in the operator guide:

- The single production path that may invoke `register` mode is
  `MemoryWriteService.configureProjectBudget(input)`. Every other
  public method (`remember`, `updateMemory`, `searchMemory`,
  `getMemoryBudget`, `exportMemoryContext`, …) calls either `lookup`
  or `strict_existing`.
- CLI `agent-recall project register <path>` is the operator-facing
  alias. It calls the same `configureProjectBudget` path.
- MCP has no public tool that registers a project. The
  `memory://health` resource surfaces `strict_isolation: true` so a
  client can verify the resolver is in strict mode at runtime.

### Apply-time identity revalidation

`applyImport`'s existing revalidation block (currently revisions +
aggregate budget) gains one new step. Concretely:

```text
service.store.transaction(() => {
  // Existing:
  //   1. re-read live revisions for every replacement, throw on drift
  //   2. sample live budget usage, re-project, throw on drift
  // New (this PR):
  //   3. for every (project_id, project_path) in plan.scopes, call
  //      identityResolver.resolve({scope:'project', project_id,
  //      project_path}, 'strict_existing'); on mismatch (observed
  //      canonical_path !== plan.expected_path OR identity absent),
  //      throw 'identity_drift'
  //   4. attach { outcome, conflicts } to every audit_events.metadata
  //      for the batch
})
```

The revalidation runs **after** the live-row checks because a missing
identity at revalidation time is a stronger signal than a drifted
budget — the order is deliberate.

### Tests + TDD ordering

1. **RED** — write `v113-identity-side-effect-free.test.ts` with the
   18 tests *failing against the current implementation*:
   - 4 × zero-writes tests for `lookup` (project_id-only / path-only /
     id+path / unknown path)
   - 4 × zero-writes tests for `strict_existing` (same matrix)
   - 2 × `register`-only mutation tests (id+path happy path;
     id+path mismatch)
   - 2 × cross-platform determinism (Windows case-folded alias
     resolves identically to mixed-case; macOS / Linux case-sensitive
     mismatch is *not* silently merged)
   - 2 × concurrent preflight / apply drift tests (use a Vitest fake
     timer + a forced `getProjectIdentity` override to simulate the
     drift)
   - 4 × preflight snapshot tests (BEFORE / AFTER row-count diff on
     every project-related table after a rejected preflight)

   and gate the upsert. Re-run; expect 18 green, 0 new failures.
3. **REFACTOR** — extract the per-mode decision logic into a private
   helper if `resolveMemoryScopeWithStore` exceeds ~80 lines. Extract
   the apply-time revalidation block into a named helper so the
   future #34 evidence work can call it without inlining.
4. **RED → GREEN** for the apply-time revalidation: extend
   `p1-atomic-import.test.ts` with a `identity_drift` test that

6. **RED → GREEN** for the audit-metadata trail: extend

### Regression risk

The existing 757+ tests cover the v1.1.2 surface. The behaviours most
at risk:

- `p3-project-identity-strict.test.ts` (14 tests) — the v1.1.2 strict
  contract; the new mode gating must keep every test green. Action:
  re-read each test, walk through the new matrix, fix any test that
  relied on the buggy side-effect-on-strict path.
- `p3-import-preflight-budget.test.ts` (12 tests) — the v1.1.2
  preflight + budget surface. The new preflight must continue to
  reject `aggregate_budget` failures without any budget mutation.
  Action: extend with the snapshot-diff test in step 1 above.
- `p1-atomic-import.test.ts` — atomicity contract. The new
  revalidation step must roll back the entire batch on identity drift
  without breaking the existing revision-drift and budget-drift tests.
  Action: walk through each test, ensure the new step runs after the
  existing checks.
- `p3-import-batch-lineage.test.ts` (14 tests) — the lineage surface.
  The new `identity_revalidation` metadata must not collide with
  existing keys (`import_batch_id`, `bundle_hash`, `bundle_version`,
  `imported_from_actor`, `imported_from_event_id`, `imported_by`).
- `p3-strict-import.test.ts` — capability + secret detection surface.
  No mode changes here; the existing tests must stay green.
- `mcp-v2-contract.test.ts` + `cli/export.test.ts` — the `register`
  path used by `configureProjectBudget` must continue to register
  idempotently. Action: confirm `mode === "register"` keeps the
  existing insert-once / update-once behaviour.
- `p2-project-identity.test.ts` — the v1.1.1 PR-2 surface. The legacy
  store-less tail must remain available for tests that exercise it;
  no test should break.

The TDD ordering above is designed to surface regressions in the
*first* test run after GREEN, not after the whole refactor.

## [1.1.3] — v1.1.3 GATE-01: side-effect-free project identity
resolution (issue #31)

### Changed

- `ProjectIdentityResolver.resolve(..., mode)` now actually respects
  the `mode` argument. `lookup` and `strict_existing` produce zero
  database writes on success and failure; `register` is the only mode
  allowed to insert into `project_identities` / `project_aliases_new`.
- `resolveMemoryScopeWithStore` gained a required `mode` parameter;
  production call sites now pass the correct mode. The legacy
  store-less tail is removed from production paths.
- `preflightImport` is now provably side-effect free: an unknown
  `project_id` / `project_path` leaves zero rows in any project-related
  table (asserted by the new snapshot-diff test).
- `applyImport` revalidates the identity binding alongside revision
  and aggregate-budget checks, all in one transaction. Identity drift
  between preflight and apply throws `identity_drift` and rolls back.

- New `ResolveError` member: `"identity_drift"` (raised only from the
  apply transaction).
- `ImportBatchRow.audit_metadata.identity_revalidation` records the
  revalidation outcome on every applied batch.
- `docs/adr/0004-identity-resolution-modes.md` documents the three
  modes, the canonical registration path, and the v1.1.2 carve-out
  this PR closes.
