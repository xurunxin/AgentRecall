# v1.1.3 Follow-up Final Gate — High-level Fix Plan

Date: 2026-07-28
Parent issue: [#30 — V1.1.3 Follow-up Final Gate](https://github.com/xurunxin/AgentRecall/issues/30)
Scope: **whole gate**, 8 sub-issues across 3 phases (no per-sub-issue code design here)
Predecessor: v1.1.2 release (`main` head `e4cbf15`)
Branch line: each sub-issue gets its own short-lived feature branch; final
candidate commit is frozen only after #31–#37 merge.

---

## Why this plan exists

The post-v1.1.2 audit reopened the gate. The previous gate (#19) closed
without synchronizing the sub-issues (#20–#29) because the parent/child
relationship lived only in a Markdown checklist — closing the parent did
not close the children, so a child could silently drift to "open" after
publication.

#30 replaces that gate with **native GitHub sub-issues** (#31–#38),
each declaring `Parent Gate: #30`, and refuses to close until:

1. each child issue is closed with merged evidence;
2. one exact release commit passes the 3-OS release-candidate matrix
   with no skipped / filtered / placeholder evidence;
3. `package.json`, `package-lock.json`, MCP handshake, tool metadata,
   CLI version, evidence, tag, and release title all agree on
   `1.1.3`;
4. a new immutable annotated `v1.1.3` tag points at that commit and
   **no previous tag is moved**.

The audit also surfaced eight concrete contracts that v1.1.2 either
shipped partially or skipped. Each sub-issue owns exactly one of those
contracts (or one release-publication step), so this plan is the
**sequencing + verification matrix** that drives the gate to a
single green commit.

## Out of scope

- Detailed code design for any one sub-issue. Per the user, this is the
  whole-gate plan only. Each sub-issue gets its own brainstorm →
  spec → plan cycle when its lane opens.
- New dependencies. All sub-issues must be implementable on the current
  dependency set (`@modelcontextprotocol/sdk ^1.29.0`, `zod ^4.0.0`,
  Node 18+ stdlib).
- npm publication. `package.json` stays `private: true`; GitHub
  release artefacts remain the canonical distribution surface.

## Sequencing + dispatch model

Each sub-issue is **a separate PR** on a separate branch line
(e.g. `feat/v1.1.3-gate-01-identity`, `feat/v1.1.3-gate-02-capability`,
...). After #31–#37 merge, the candidate commit is frozen on `main`
and pushed to an `rc-*` branch with **no further feature changes** —
#38 then drives #30 to closure.

```text
Phase A (parallel then sequential)
  Lane A1 ─► #31 identity      ─┐
  Lane A2 ─► #32 capability    ─┼─► Lane A3 ─► #33 sensitivity
                                 │
Phase B (parallel then sequential)
  Lane B1 ─► #34 evidence      ─┐
  Lane B2 ─► #36 deterministic ─┼─► Lane AB ─► #35 tag/version
                                 │
Phase C (sequential)
                                 ▼
                Lane C1 ─► #37 docs   ◄──── (after A + B stable)
                                 │
                Lane C2 ─► #38 exact-SHA release  ◄── #37 merged
                                 │
                                 ▼
                           close #30 (gate)
```

Phases are the **logical grouping** from #30's body; lanes are the
**implementation sequence** (one lane = one PR). A1 + A2 are the
two parallel starters in Phase A; A3 is sequential after both merge.

Why this split:

- **#31 and #32 have no production-code interlock** (identity and
  capability are separate subsystems). They can run on two parallel
  PRs.
- **#33 blocks on #31 + #32** because it must thread *the*
  authorization model (#32) through every path *after* the strict
  identity surface (#31) is side-effect free. Doing #33 first would
  re-thread the policy twice.
- **#34 and #36 also unblock each other only at the test-result
  interface** — both need real, unsuppressed green result fragments
  to feed the aggregator, but their **implementation** does not
  conflict. They run in parallel.
- **#35 blocks on #34** (canonical evidence is the input) but is
  orthogonal to #36 (the result fragments only need to exist, not
  be aggregated yet).
- **#37 is sequential after A + B** because the documentation
  describes the runtime + release contracts those lanes ship.
- **#38 is the only "run the matrix" lane** and must run last; it
  is also the only lane that actually creates the `v1.1.3` tag.

## Per-sub-issue target contract

For each sub-issue, this plan commits to **one acceptance gate** that
the sub-issue's own spec/plan must satisfy before its PR merges. The
per-sub-issue detail (file-level design, TDD cases, regression risk)
lives in that sub-issue's own `docs/superpowers/specs/<date>-<topic>.md`
when its lane opens.

### #31 — project identity lookup and strict modes side-effect free

**Goal.** `ProjectIdentityResolver.resolve()` exposes three named
modes with hard contracts: `lookup` and `strict_existing` are
pure-read (zero DB writes on success *and* failure); `register` is
the only mode allowed to insert into `project_identities` /
`project_aliases_new`. Import preflight becomes side-effect free;
import apply revalidates the exact identity binding inside the same
transaction as revisions + aggregate budget.

**Acceptance gate.**

- Before/after table snapshots prove `lookup` / `strict_existing`
  produce zero writes in success *and* failure paths.
- An unknown `project_id` / `project_path` under strict mode leaves
  no rows in any project-related table.
- An `id+path` mismatch returns `project_identity_conflict` and
  mutates nothing.
- Identity drift between preflight and apply rolls the entire
  import transaction back.
- Cross-platform determinism (Linux / macOS / Windows case-folding)
  pinned by a test.
- The canonical "register a project" path is documented and is the
  *only* path through which `configureProjectBudget` /
  `registerAlias` is invoked from production code.

**Owns.** `src/scope-resolver.ts`, `src/services/memory-write-service.ts`,
`src/services/memory-read-service.ts`, `src/portability/importer.ts`,
all callers of `ProjectIdentityResolver`.

### #32 — profile-scoped admin capability + capability-file permission validation

**Goal.** Active profile becomes an explicit input to the service /
security context. Core and Extended processes never gain restricted
visibility from the mere existence of `admin.cap`. Admin refuses to
start when the capability file is missing / malformed / symlinked /
wrong-owner / overly permissive / ACL-drifted. Token bytes never
appear in logs, audit, errors, or status payloads.

**Acceptance gate.**

- Core + Extended packaged black-box suites remain normal visibility
  even with a valid `admin.cap` on disk.
- Admin refuses to start under each of: missing file, malformed
  JSON, symlinked file, wrong POSIX owner, `0644` / group-readable
  mode, wrong Windows owner / ACL drift (asserted in Windows CI).
- Privileged writes reject missing / malformed / mismatched /
  wrong-type capabilities with stable denial codes; denial is
  audited (actor + request + reason) without token material.
- Constant-time token comparison in production code paths.
- Revoke + re-grant + restart semantics deterministic; documented.
- README + ADR state this is local operator separation, **not**
  cryptographic multi-user security.

**Owns.** Capability loader (POSIX `fs.stat` + Windows ACL probe),
service-context construction, every `hasCapability()` call site.

### #33 — one sensitivity policy across read / export / resource / maintenance

**Goal.** One canonical authorization result (including maximum
visible sensitivity) threaded through every content-bearing path.
Filtering happens at or before the Store / SQL boundary, never only
at response rendering. Maintenance helpers, diagnostics, exports,
Markdown index, and the MCP resource surfaces all honour the same
ordering.

**Acceptance gate.**

- Central visibility matrix (Core / Extended / Admin × public /
  private / restricted) matches test assertions exactly.
- Core cannot read or infer restricted / private content via *any*
  tool, resource, CLI command, context pack, maintenance result, or
  exported Markdown.
- `find_duplicates`, maintenance `plan` / `apply`, `rebuild_markdown_index`,
  context export all respect the same boundary.
- Hidden rows are absent at the SQL layer (verified by SQL-boundary
  test, not only by response rendering).
- Unauthorized errors carry stable codes and no row-derived secret
  fields (title / tags / source ref / sensitivity / counts of hidden
  rows).
- Documentation table matches packaged black-box assertions.

**Depends on.** #32 (auth model is the input).
**Owns.** `MemoryReadService`, `MemoryMaintenanceService`,
`MemoryDiagnosticsService`, `src/mcp/resources.ts`,
`src/cli/commands/*` content paths, Markdown export.

### #34 — release evidence fail closed and internally consistent

**Goal.** One canonical platform vocabulary
(`linux-x64` / `darwin-x64` / `win32-x64`) across workflow matrix,
artifact filenames, hash manifest, evidence schema, validators,
release notes, and docs. Versioned `release-evidence.json` schema
where `artifacts` and `sha256_checksums` are distinct validated
types. No `local://` URLs in stable evidence. Test totals and
migration summaries derived from real result fragments, not hard-coded
constants.

**Acceptance gate.**

- One canonical Windows suffix used in candidate workflow, release
  workflow, scripts, validators, docs, and filenames (verified by
  grep-equivalent release-gate test).
- A real three-platform fragment set aggregates into evidence
  accepted by the verifier.
- Array-where-object-required is rejected (negative fixture).
- Missing / partial platform artifacts fail the gate.
- A changed artifact byte fails independent SHA-256 verification.
- Stable evidence with any `local://` URL is rejected.
- Test / migration counts come from real fragments; fallback to
  constants fails.
- Publication preparation fails when verified candidate evidence is
  absent or references a different SHA / version.
- Candidate and tag workflows validate the **same** evidence schema.

**Owns.** `.github/workflows/release-candidate.yml`,
`.github/workflows/release.yml`, `scripts/release-evidence.mjs`,
`scripts/verify-release-evidence.mjs`, `scripts/compute-artifact-hashes.mjs`,
`scripts/extract-release-artifact.mjs`, all evidence-related
config + tests.

### #35 — version metadata + immutable tag publication reproducible

**Goal.** `1.1.3` everywhere (`package.json`, `package-lock.json`,
MCP handshake, tool metadata, CLI version, evidence, release title,
tag). Annotated-tag creation uses valid Git commands + temporary
author/committer environment without mutating global Git config.
Refuse to create a tag that already exists locally or remotely.
Verified release evidence is required for non-dry-run tag creation.
Tag commit SHA = candidate SHA = release-evidence SHA = checked-out
HEAD.

**Acceptance gate.**

- `package.json`, `package-lock.json`, MCP handshake, tool metadata,
  CLI version, evidence, release title, tag all report `1.1.3`.
- Version-consistency test fails when any one source is changed
  independently.
- Tag script creates a valid annotated tag in a temporary test
  repo; never uses unsupported Git flags; never modifies user /
  global Git config.
- Existing local or remote tags cause a hard failure (no force,
  no delete, no recreate).
- Missing / local-placeholder / stale-SHA / failed evidence
  prevents tag creation.
- New tag points exactly at the verified candidate SHA.
- Downloaded archives report `1.1.3` from their own packaged
  metadata + runtime.
- No prior tag is moved.

**Depends on.** #34 (canonical evidence is the input).
**Owns.** `package.json`, `package-lock.json`, `scripts/prepare-release.mjs`,
tag-creation tool, server / tool metadata surface, version-consistency
test.

### #36 — heartbeat suppression removed; orchestration deterministic

**Goal.** Release-critical jobs do not import the heartbeat-filter
proxy. Heartbeat timeouts and synthetic unhandled rejections make
the job fail. Heavyweight suites are split into separate auditable
result groups: unit/integration, MCP black-box, migrations, stress
release profile, extracted-artifact lifecycle. 10,000-operation
stress runs once per intended release job. Cleanup + diagnostic
artifacts kept even on failure. JSON / JUnit fragments uploaded for
every group, including failed groups.

**Acceptance gate.**

- No release-critical job imports `test/setup/heartbeat-filter.ts`
  or equivalent.
- Synthetic unhandled rejection ⇒ job fails.
- Synthetic Vitest worker timeout ⇒ job fails.
- Unit/integration, black-box, migrations, stress, packaged-artifact
  suites are separate, auditable result groups.
- 8-process / 10,000-op stress passes on Linux + macOS + Windows
  without heartbeat filtering.
- No release-critical test skipped for missing `dist`, missing
  artifact, missing profile, or unavailable environment.
- Every spawned MCP / worker process cleaned up on success *and*
  failure.
- Result fragments uploaded for every group, including failed ones.
- Evidence aggregator consumes only unsuppressed green fragments.

**Owns.** Vitest config, `test/setup/*`, multi-process stress suite,
`.github/workflows/release-candidate.yml` job topology,
result-fragment upload wiring.

**Depends on.** #31–#36 (the docs describe the contracts those

**Owns.** `README.md`, `CHANGELOG.md`, `docs/guides/*`,

## What each sub-issue's own spec must contain (when its lane opens)

This whole-gate plan is the **sequencing + acceptance** layer. When a
lane opens, the agent working that lane writes the file-level design
to its own `docs/superpowers/specs/<date>-v1.1.3-<topic>.md`. Minimum
sections:

1. **Why** — link back to this gate plan + the relevant sub-issue.
2. **Files to change** — concrete file paths + whether each is added,
   modified, or removed.
3. **Public surface delta** — exported types, MCP tools / resources,
   CLI commands, env vars.
4. **TDD plan** — failing tests first, in the order:
   red (write failing test for one acceptance bullet), green (smallest
   change that passes), refactor (only after green).
5. **Regression risk** — list of existing tests that could break and
   how the lane will keep them green.
6. **CHANGELOG entry draft** — the bullet the lane will append, in the
   project's existing changelog style.
7. **Evidence to attach to the closing sub-issue comment** — exact
   test command + result fragment path.

The whole-gate plan does not duplicate those per-sub-issue details.
It only guarantees that **the lane sequence + the final acceptance
matrix are stable** before any lane opens.
