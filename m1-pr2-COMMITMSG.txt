feat(project-identity): strict binding + aliases + conflict protection

Stage 15 PR-M1-2 (issue #7, spec § 5.4).

Pre-PR-M1-2 had three correctness gaps in the
project identity model:

  1. The resolver derived a `project_id` from a
     hash of `project_path`. Two callers in the
     same repo could land in two different
     identities; a caller with a stale
     `project_id` could silently mutate a sibling
     project's data.
  2. There was no enforcement that a
     `project_id` + `project_path` triple matches
     an existing binding.
  3. Symlink / worktree / Windows case differences
     were handled inconsistently.

This PR introduces a strict project identity
model:

  - **Schema v7 → v8**: `project_identities`
    (one row per `project_id` with its
    `canonical_path`) +
    `project_aliases_new` (PRIMARY KEY on the
    raw alias path; FK to
    `project_identities(project_id)`).
  - **Resolver flow**:
    1. canonicalise the caller's `project_path`
       (resolve + realpath + symlink resolution +
       Windows case-fold);
    2. lookup `project_identities` by the
       caller's `project_id` — if the row exists,
       its `canonical_path` is the source of
       truth; if not, register a new identity;
    3. lookup `project_aliases_new` by the
       canonical path — if the row points to a
       *different* `project_id`, surface
       `project_identity_conflict`;
    4. worktree handling: when the caller's path
       is a separate directory that shares a
       `git rev-parse HEAD` with the identity's
       canonical path, register a `worktree`-kind
       alias.
  - The resolver returns the canonical path
    (`project_path` in `ResolvedScope` is the
    identity's canonical path, not the caller's
    raw path).
  - **`project_identity_conflict`** is the stable
    error code (added to `STABLE_ERROR_CODES` in
    `src/tools/error-codes.ts`; permanent,
    retryable=false).
  - **`invalid_alias`** is a sibling stable code
    for alias binding conflicts; permanent,
    retryable=false.
